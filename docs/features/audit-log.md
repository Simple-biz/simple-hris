# The Audit Log

*Added 2026-09-09. The mechanism itself — who writes an event, what an event may
say, who can read it, how long it lives. For WHO MAY OPEN a dashboard see
`route-authorization.md`; for the delete-specific policy on PAB disputes and
leave requests see `delete-authorization.md`.*

Before this doc existed the mechanism had no governing rules at all: the table's
consumers each kept their own private idea of what an action name meant, and the
question "is this write audited?" had no answer except grepping.

---

## 1. The table

`public.audit_log`, append-only, one row per audited action, reaching back to
**2026-06-06**.

| Column | Notes |
|---|---|
| `user_name` | **The actor.** An email for a signed-in person; some legacy rows carry a display name. |
| `user_role` | The actor's first role at the time of the action. |
| `action` | Dotted family name, e.g. `orphanage_registry.deleted`. See §2. |
| `resource` | The table or bucket touched. |
| `resource_id` | Usually the row id, or the **email** for person-scoped actions — this is what makes an exact per-person lookup possible with no recency ceiling. |
| `details` | jsonb. Free-shaped per action. |
| `ip_address` | Set on ~40% of rows. It is the **only** signal separating a staff-entered change from the employee's own submission on flows that share an action name. |
| `created_at` | UTC. Day filters are Asia/Manila days (`+08:00`). |

> `user_email`, `target_email`, `event_type` and `user_id` exist on the table and
> are populated on **0 of 17,741 rows**. Do not select them.
> (memory/penny-audit-log-visibility.md)

## 2. The action registry is the source of truth

**`src/lib/audit/registry.ts`.** Every action belongs to a *family* (a dotted
prefix) and every family names the *dashboards* it is raised on.

This is consumed by:

- the Admin **Audit Log** panel — its dashboard filter and every row badge;
- Admin Penny's **`search_audit_log`** tool — its whole `ACTION FAMILIES` block
  is generated by `describeAuditFamilies()`, and its `surface` parameter is
  enumerated from `AUDIT_SURFACES`.

Both used to keep their own hand-written copy, and both had already drifted:

- the panel's 14 predicates claimed **no** `orphanage.*`, `wizard.*`,
  `dispatch.*`, `documents.*`, `people.*`, `bank_*`, `ticket.*`,
  `time_adjustment.*`, `feature_permission.*` or `*_assistant.*` action, so
  those rows appeared only under "All activity" and wore no badge;
- the tool description named `master.add`, `announcement.*` and `gift.*` shapes
  that did not exist while omitting three of the largest real families.

### Rules

1. **Longest match wins.** `orphanage_registry.deleted` resolves to
   `orphanage_registry.`, not `orphanage.`, regardless of array order. The old
   panel depended on ordering ("listed before `csv` so `csv.rates.sync` is
   tagged as a sync"), which stops being true the moment anyone re-sorts.
2. **An unregistered action resolves to `null`**, never to a default bucket. The
   panel labels it `Unregistered` on purpose.
3. **A new audited action must be registered** — `src/lib/audit/registry.test.ts`
   source-scans every `insertAuditLog` / `insertAuditLogs` call site in `app/`
   and `src/` and fails the build on an action with no family. It runs a
   negative control first (a scan that matched nothing would report perfect
   coverage of an empty set) and handles ternary and template-literal actions.
4. A family may list **several dashboards** — a PAB dispute is filed on
   Orphanage and decided on Accounting, and both teams look under their own name.

### Adding an action

```ts
// 1. src/lib/audit/registry.ts
{ match: 'my_thing.', surfaces: ['accounting'], label: 'My thing', note: 'saved/deleted' },

// 2. the route
const authz = await requireFeatureEdit('accounting', 'something');
if (!authz.ok) return deniedResponse(authz);
void insertAuditLog({
  ...auditFrom(request, authz),   // actor + IP, one place
  action: 'my_thing.saved',
  resource: 'my_table',
  resource_id: row.id,
  details: { … },
});

// 3. npm test  → registry.test.ts proves it is reachable from the panel + Penny
```

`AuditAction` in `src/lib/supabase/audit-log.ts` is still typed
`AuditAction | string`, so the compiler does not enforce the name. **The
registry test is the guard** — Kane's 2026-09-09 call, over declaring all ~150
live names in the union (see §8).

## 3. Writing an event

### The actor comes from the authorization gate

```ts
import { auditFrom } from '@/lib/audit/context';
…
void insertAuditLog({ ...auditFrom(request, authz), action, resource });
```

`auditFrom(request, authz)` takes an **`AuthzOk`**, whose `sessionEmail` is a
non-optional `string`. Once a route has narrowed past
`if (!authz.ok) return deniedResponse(authz)` there is no "missing actor" branch
to fall through, which is the point.

- **Never from the request body.** Six routes on the Orphanage/HR gift and
  orphanage-budget surfaces used to take `edited_by` / `decided_by` /
  `submitter_email` / `created_by` off the body as the audit actor — a
  client-supplied identity is a forged one. The body value, where it is also a
  business fact (`decided_by` on a budget request row), stays on the ROW and is
  recorded in `details` as a *claim*; the actor is the session.
- `getSessionActor()` **fails open** to `{ user_name: 'anonymous' }` inside its
  own `try/catch`. It remains for paths with no `AuthzOk` (the public
  bank-update link, employee self-service), never as a second lookup in a route
  whose gate already resolved an identity.
- The IP comes from `clientIp(request)` — one implementation, `x-forwarded-for`
  first hop then `x-real-ip`. It used to be re-derived by hand in 30+ routes,
  which is why `ip_address` is set on only ~40% of historical rows.

### An event that fails to write is shouted about

`insertAuditLog` logs `[audit] write FAILED — event lost` with the action and
resource. 182 of the 228 call sites are `void insertAuditLog(...)`, so the
returned `{ error }` was previously read by nobody and a lost event was
indistinguishable from an action that never happened.

### Destructive paths audit FIRST

`delete-authorization.md` requires the event to carry the prior row "so
deletions remain traceable after the row is gone". That is only achievable if
the snapshot is taken **and written** while the row still exists, so on these
paths the audit write is awaited and **the delete is abandoned if it fails**:

| Path | Action | Snapshot |
|---|---|---|
| `DELETE /api/orphanages/[id]` | `orphanage_registry.deleted` | whole row, account number masked to last-4 |
| `DELETE /api/bonus-catalog?type=bonus` | `bonus_catalog.definition.deleted` | the definition + the ids of the assignments it cascades to (the version history goes too) |
| `DELETE /api/payment-catalog/system-bonuses` | `system_bonus.deleted` | the custom variant |
| `DELETE /api/hsl-bonus/period` | `hsl_bonus.period_deleted` | every scored entry, the dept-period total, the status rows |
| `DELETE /api/audit-log` | `audit.purged` | cutoff + row count (§5) |

`DELETE /api/hsl-bonus/entries` (one person) snapshots the scored row but does
not block the delete on the audit write — a single entry, and the period wipe
above is the destructive case.

### Settings are audited by KEY, on the server

`POST /api/app-settings` writes an **`app_settings.changed`** row for every
write that changes a value, **whoever the caller is** — Payroll Wizard, System
Settings, Admin. The decision is by key (`isAppSettingChangeAudited`,
`src/lib/audit/app-settings-change.ts`), so **a key added tomorrow is audited by
default**; the only keys left out are the derived snapshots in
`APP_SETTING_AUDIT_EXEMPT` (§6), pinned exactly by
`app-settings-change.test.ts`, and that test also lists every key the wizard
writes and asserts each one is audited.

- `resource_id` = the key; `details` = `key`, `before`, `after`, `created`.
  The old value is read immediately before the upsert — a plain read, not a
  compare-and-swap, so a write racing it can make `before` a revision stale.
- A value over **4,000 characters** is summarised: `before_length`,
  `after_length`, and the top-level JSON keys that moved (`changed_keys`, first
  100, with `changed_keys_total`).
- A failed pre-read never blocks the save and never reads as "unchanged" or
  "created": the row carries `before_unavailable: true` and no `before`.
- Re-posting the same value writes nothing — the `/api/pab-exclusions` rule.
- Per-cycle keys (`payroll.wizard.<x>.<file>.csv`) carry `details.cycle.source_file`,
  so they also appear in that week's Step 9 audit trail.
- The policed families (payroll lock, sensitive, `secret.`) keep their own
  branch and redaction; this branch never sees them.
- Written **after** the upsert succeeds and **awaited** (a `void` insert can be
  cut off with the response).

Why: until 2026-09-28 the route audited only the policed families, so the PAB
Period, the Tech Bonus payout week, the US holiday list, the Step-7 "Do not pay"
set and the cycle FX record moved with no trail. "Who changed the PAB Period?"
could only be answered by inference from `wizard.opened`, and the previous window
was gone (session log item 239).

The wizard's own `wizard.fx_rate_changed`, `wizard.config.dept_pay` and
`settings.ot.department` client rows stay — they carry the cycle context and the
operator's intent — so those three saves now leave **two** rows. The server row
is the one that cannot be skipped.

### The additions save is diffed on the server

`POST /api/payroll-wizard/additions` — the blob that PAYS — writes
**`wizard.additions_saved`** after its compare-and-swap succeeds: every changed
leaf by path (`bonusOverrides/<email>/adjustment`, `deptMetrics/lead_gen/appointmentsSet`,
`techBonusManualRevokes` as added/removed members), the people it touched, and
`before_exact` (false when another save landed between the route's read and its
write). `pabStatusSnapshot` is derived, so it is counted, not itemised. Lists are
capped (200 changes, 100 people) with uncapped totals. `describeAdditionsSave`,
`src/lib/payroll/wizard-additions-audit.ts`.

The client's per-edit `logAudit` calls cover five updaters. Every KPI metric
modal, the Adj. note text, the Tech revoke/restore chips and the Notes-board
auto pre-fill changed pay with no row at all; the server diff records whatever
landed, whichever path produced it. A refused (409) save writes nothing.

### Money and secrets in `details`

The audit log has a wider readership than the surface an event came from.

- Bank account numbers are reduced to `···1234` with `maskAccountLast4`
  (`src/lib/payroll/mask-account.ts`, the ONE masker).
- Shipping addresses, rated assistant replies and note text are **not** copied
  into `details`; they live on their own rows. `employee_gift_shipping.submitted`
  records the `channel` (`employee_self` / `staff`) and the fields touched,
  because that distinction is the thing that cannot be recovered later.
- `ReadinessActivityFeed` renders fixed label templates and **never prints
  `details`** — that pane is reachable with a view-only grant
  (memory/readiness-activity-feed.md).

## 4. Reading it

### `GET /api/audit-log` (elevated: admin / accounting / hr_coordinator)

| Param | Meaning |
|---|---|
| `surface` | One of `AUDIT_SURFACES` — expands to that dashboard's prefixes via the registry |
| `action_prefix` | Comma-separated prefixes; wins over `surface` |
| `actor` | Exact for an email, contains-match otherwise |
| `search` | Free text over action / resource / actor / `details` |
| `since`, `until` | `YYYY-MM-DD`, Asia/Manila days |
| `before` | Keyset cursor — a previous page's `next_cursor` |
| `limit` | 1–500, default 100 |

**Filtering is server-side and paging is keyset.** The panel used to load the
newest 500 rows and filter them in the browser, so over a 17k-row table any
question about an older event answered "no results" — the same "a window
presented as history" failure that
memory/penny-audit-log-visibility.md fixed for Penny's tools and left standing
on the human-facing panel. Keyset, not `.range()`, because PostgREST silently
truncates at 1000 rows (memory/postgrest-1000-cap-sweep.md).

**`search` states its window.** A free-text term cannot go into SQL (`details`
keys vary per action), so it filters a wider server-side window (2000 events)
in JS and the response carries `search_window`. When that window did not reach
the end of the table the panel shows an amber banner saying how far it got. An
unstated window is exactly how "no results" gets mistaken for "never happened".

### Admin Penny

`search_audit_log` (+ `surface`), `list_audit_actions` (reads the live table, so
it cannot rot), `get_change_timeline`, `get_payroll_notes_history`,
`get_bank_change_history`, `get_rate_history`, `get_transfer_history`,
`get_onboarding_info`. Every returned row now also carries the registry's own
`surface` and `family`, so Penny names an event the way the panel's badge does
instead of guessing from the action string.

Adding a TOOL (not an action) additionally requires a `TOOL_PHASES` phrase or
`console-phases.test.ts` fails — `admin-penny-console.md`.

## 5. Retention

**There is no "clear the log".** `DELETE /api/audit-log` is a retention purge:

- `older_than_days` is **required**, and anything under
  `AUDIT_PURGE_MIN_AGE_DAYS` (**90**) is refused;
- `preview=1` counts without deleting (the panel previews before offering the
  button);
- the `audit.purged` event — cutoff, days, row count, actor, IP — is written
  **before** the delete, and the purge is abandoned if that write fails.

The old `clearAuditLog()` truncated the entire table behind a "Clear Log"
button. It was the most destructive action in the app and the one action that
could not, by construction, record itself. Kane chose the retention purge on
2026-09-09 over keeping the wipe with an `audit.cleared` row.

> Anything that must survive a purge does not belong in `audit_log`. The
> termination write-back undo data lives in
> `termination_documents.field_writebacks` for exactly this reason.

## 6. Deliberately NOT audited

Silence has to be a decision, or the next reader treats a gap as a bug.

| Path | Why |
|---|---|
| HSL/KPI **score saves** (`POST /api/hsl-bonus/entries`) | Autosave volume. Standing ruling: memory/readiness-activity-feed.md. A manager mid-scoring appears at Mark Ready / Lock, which ARE audited (`payroll.kpi.*`). |
| `POST /api/accounting/overview-snapshot` | Fires on every Accounting Overview load and decides nothing — it republishes a figure computed from audited inputs. |
| `POST /api/hr/workspace-account/verify` | Read-only probe against Google Workspace; mutates nothing. |
| `POST /api/hr/work-email/suggest` | Pure computation; mutates nothing. |
| `POST /api/presence/heartbeat` | Per-minute liveness. Never relabel it as a sign-in record (memory/last-signed-in-not-recorded.md). |
| Notification reads / `clear-all` | Per-viewer UI state. |
| `app_settings` `payroll.wizard.final_pay.<file>` | The wizard republishes it **automatically** 1.5 s after any change, and it is whole-payroll sized. It is computed from audited inputs (`wizard.additions_saved`, `app_settings.changed`, `csv.*`), and staging it for dispatch is audited as `paystubs.staged`. Exempt in `APP_SETTING_AUDIT_EXEMPT`, 2026-09-28. |
| `app_settings` `hubstaff_daily_breakdown` | A by-product of the Hubstaff ingest, which is audited as `csv.upload`. Exempt in `APP_SETTING_AUDIT_EXEMPT`, 2026-09-28. |
| `GET /api/payroll-wizard/notes` seeding / trimming blank rows | Housekeeping of EMPTY rows on read; a row with content is audited when it is written (`accounting.payroll_wizard_notes.*`). |

## 8. Open

- **`POST /api/import-daily-report` is a dead endpoint.** No component fetches
  it; the Diagnostics "Daily Report Import" probe only reads what it produced.
  It is now gated (`requireElevatedSession`) and audited, but the right end state
  is deletion — **Kane's call**.
- **`AuditAction | string`** still accepts any string. The registry test is the
  guard; declaring all ~150 live names in the union (and retyping the 8
  template-literal call sites as template literal types) is the stronger fix and
  was explicitly deferred on 2026-09-09.
- **`src/lib/mesa/receipts.ts` and `notify-failure-audit.ts`** take an `actor`
  parameter with a fallback (`params.actor?.user_name ?? …`). Server-supplied,
  not body-supplied, so not a forgery — but not an `AuthzOk` either.
- **Payroll Wizard's Notes pane — the embedded manager calculators** (Readiness →
  score it) write `/api/bonus-catalog-applied`, `/api/qc/submissions` and
  `POST /api/hsl-bonus/entries` with no row. The HSL entry save is the standing
  score-save ruling (§6); the other two were **not decided** in the 2026-09-28
  pass, which stopped at the wizard itself (session log item 240).
- **Most audit writes are still fire-and-forget** (`void insertAuditLog`, and the
  client's `logAudit` swallows errors), so a row can be lost with only a console
  line. The 2026-09-28 server writes are awaited; the older ones were not touched.
- The Admin panel's dashboard chips carry **no counts**. A count over the loaded
  window dressed up as a total is what the old panel showed; a real per-surface
  total needs a server-side aggregate that does not exist yet.
